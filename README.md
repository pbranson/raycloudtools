## Ray Cloud Tools
A set of command line tools for processing ray clouds, together with an associated C++ library.


Ray clouds are point clouds with the sensor origin stored per point (currently encoded in the 'normal' field of .ply files).
Ray clouds represent free space as well as surfaces. This allows processing that cannot be done on point cloud data alone.

This is an open-source research library, a place to release new techniques in ray cloud analysis and manipulation. So if you would like to contribute with a new or improved method, do suggest it in our discussions page: https://github.com/csiro-robotics/raycloudtools/discussions.

## Install using a Pre-built Container

### Docker (Linux, MacOS, Windows)
#### Pull the Latest Image
To download the latest image from GitHub Packages, use the following command:
```bash
docker pull ghcr.io/csiro-robotics/raycloudtools:latest
```

#### Run an Interactive Container
To run the container interactively and bind your home directory to a directory inside the container for accessing host files:

#### On Linux/MacOS
```bash
docker run -it --name raycloudtools -v /home/yourusername:/workspace ghcr.io/csiro-robotics/raycloudtools:latest /bin/bash
```

#### On Windows
```bash
docker run -it --name raycloudtools -v C:/Users/YourUsername:/workspace ghcr.io/csiro-robotics/raycloudtools:latest /bin/bash
```
Replace `/home/yourusername` or `C:/Users/YourUsername` with the path to your home directory.

#### Reusing Container
To restart and attach to the container in the future:
```bash
docker start -ai raycloudtools
```

## Visualising Ray Clouds:
free software such as Meshlab and CloudCompare can view ray clouds.

The build variables RAYLIB_VISTOOL and RAYLIB_IMAGETOOL allow the --view (-v) flag to view command-line results immediately.
They default to meshlab and kolourpaint respectively but can be changed with ccmake or with the -D cmake argument.
You will need to install these programs if you want the --view flag to work.

## File format:
Raycloud files are loaded and saved in binary .ply format, the header section is text and follows this format:
```console
ply
format binary_little_endian 1.0
comment generated by raycloudtools library
element vertex 0000000000<number of points>
property <float/double> x
property <float/double> y
property <float/double> z
property <float/double> time
property <float/double> nx
property <float/double> ny
property <float/double> nz
property uchar red
property uchar green
property uchar blue
property uchar alpha
end_header
```
followed by the binary data. By default it uses floats for x,y,z,nx,ny,nz and doubles for time. nx,ny,nz is the vector from the end point x,y,z to the sensor's location at the time that the point was observed. It is not a surface normal, but the ray representing free space from point to source.

Imported .ply point cloud files have a similar format, but without the nx,ny,nz fields, and optionally an intensity field instead of the red,green,blue,alpha:
```console
ply
format binary_little_endian 1.0
comment Any comment here
element vertex 0000000000<number of points>
property <float/double> x
property <float/double> y
property <float/double> z
property <float/double> time
property <float/double> intensity
end_header
```
The range of this intensity mapped onto the raycloud's 0-255 alpha value using rayimport's max_intensity optional parameter.

The imported .laz point cloud format is the 3D point, time and intensity fields. Plus the optional colour field.

<p align="center">

By default density assumes a spherical (isotropic) distribution of leaf angles (G = 0.5), giving leaf area per volume. For vertical stem-like elements such as mangrove pneumatophores, use `--density_model vertical_cylinder`. This applies G = sin(zenith) to each ray, so density is the frontal area per volume N·d (stems per m² × diameter, in m⁻¹), and pixel values are the frontal area index N·d·h. Ground returns should be removed first (e.g. with a `rayextract terrain` mesh, setting ground rays to zero alpha; the report's Section 10 gives the commands and their cost at the stem bases), so that they count as unobstructed rays rather than hits. The method, its corrections, a synthetic validation, its known biases and a calibration procedure are in [`docs/pneumatophore_density_report.md`](docs/pneumatophore_density_report.md); large domains are in [`docs/large_scale_density.md`](docs/large_scale_density.md).

For thin stems scanned by hand-held lidar, a typical command, giving densities for 1 x 1 x 0.1 m cells, is:

```console
rayrender cloud.ply top density --density_model vertical_cylinder --estimator pooled --no_flat_top --stem_diameter 0.01 --footprint 0.01,0.003,0.05 --pixel_width 0.05 --min_bound -3,-3,0 --max_bound 3,3,0.6 --cells cells.csv --cell_size 1,1,0.1 --profile profile.csv
```

* `--stem_diameter 0.01`: the mean true stem diameter (m) at the heights analysed. The result is about as sensitive to it as to the footprint threshold.
* `--footprint exit_diameter,divergence,threshold`: corrects for the beam footprint, which makes thin stems appear wider. The exit diameter and divergence (1/e² level) are the scanner's beam specification; the threshold (the fraction of the beam's power a stem must intercept to give a return) is not published and must be calibrated.
* `--return_range surface|outline` (with `--footprint`): the range reported for a partly intercepted stem, at the stem surface (default) or where the beam axis meets the footprint-widened outline. Unverified for real scanners; results near the stem tops depend on it.
* `--estimator pooled` (recommended): Beer–Lambert hits and path pooled over a horizontal neighbourhood of (2k+1) x (2k+1) voxels, k = round(`--pool_radius` / voxel width) (±0.075 m for the default 0.05 m at 5 cm voxels), then corrected for the stems occupying space. `--estimator crossing` has no occlusion correction and reads low for dense stems with a footprint; the default `beer_lambert` (unpooled) reads high for discrete stems.
* Stem occlusion correction (with `--stem_diameter`; `--no_overlap_correction` disables it): inverts a precomputed hard-core response table. The solid fraction is limited to 0.4, so N·d ≤ 1.6 / (π d) (51 m⁻¹ for 1 cm stems). `--min_gap g` tells it that stem surfaces are at least g diameters apart.
* `--self_shadow_correction` (with `--estimator pooled` and `--stem_diameter`; off by default): corrects the pooled neighbourhoods for the shadow each stem casts within its own neighbourhood, which makes `density` read high by about 0.47 d_eff / W for a window of width W. Use it for uniform stands; in patches and along cable roots it makes `density` read low.
* Single-voxel windows for clustered stands (experimental, all off by default): `--pool_radius 0 --self_shadow_correction --self_shadow_second_order --occlusion_radius 0.05 --ratio_bias_correction --no_neighbour_priors`. `--self_shadow_second_order` uses the second-order self-shadow factor, `--occlusion_radius` inverts the occlusion correction over a larger neighbourhood, `--ratio_bias_correction` corrects each neighbourhood's hits/path for its few rays, and `--no_neighbour_priors` stops blending sparsely observed voxels with their neighbours. They read low where rays are sparse and stems dense.
* `--cells` (with `--cell_size`) and `--profile` aggregate the voxels into cells and height layers, with columns `density_frontal_area_per_volume_Nd` (the mean of the observed voxel densities: the main output), `pooled_density_frontal_area_per_volume_Nd` (hits over weighted path: path-weighted, so low where stems are patchy within a cell), `patchiness_ratio` (their ratio), `hits`, `weighted_path` and `observed_fraction`. Unobserved cells are `nan`.
* `--no_flat_top` disables the flat canopy top model (designed for grass and crops), which biases stems of varying height. `--min_sin_zenith` (default 0.1) and `--max_sin_zenith` select a band of ray angles.

Recommended: the settings above (`--estimator pooled --no_flat_top`, 5 cm voxels, measured diameter, calibrated threshold, `--min_gap` from the field); use `density`, and only cells with `observed_fraction` of at least 0.9. Add `--self_shadow_correction` for uniform stands, or use the single-voxel options for clustered stands whose lower layers are well observed. In simulation `density` reads 4–9% high for random stems without the correction (within 2% in the lowest 0.2 m with it, over the scan geometries tested), and stems along cable roots read 0.87 without it, 0.81 with it and 0.98 with single-voxel windows; see the report for these and the other residual biases.

**Large areas, and heights above sloping ground.** `raysplit cloud.ply tiles x0,y0 width halo zmin,zmax [nx,ny]` splits a cloud into tiles, each with every ray crossing it and its halo, keeping ray start points (which the footprint correction needs). `raydensity` estimates one tile and writes its chunk of a Zarr store of cells (`density`, `pooled_density`, `patchiness_ratio`, `hits`, `weighted_path`, `observed_fraction`, `solid_fraction`, and optionally voxels), readable by xarray, zarr-python and GDAL. Tiles are independent and match a single run. Split with a halo 1.5 voxels larger than `raydensity`'s (`--halo`, by default the larger of the pool and occlusion radii + 2 voxels = 0.15 m), and a height slab covering the ground relief plus `--heights`:

```console
raysplit forest.ply tiles 400000,6100000 25 0.225 1,4.3 12,12
raydensity forest_3_7.ply forest.zarr --origin 400000,6100000 --tile_width 25 --tiles 12,12 --tile 3,7 --ground forest_mesh.ply --heights 0,0.6 --stem_diameter 0.01 --footprint 0.01,0.003,0.05
```

`--origin`, `--tile_width`, `--tiles` and `--tile` are required. `raydensity` defaults to `--density_model vertical_cylinder`, `--estimator pooled` and no flat top model, and takes `--voxel`, `--cell_size`, `--return_range`, `--pool_radius`, `--min_gap`, `--self_shadow_correction` and the single-voxel options (recorded in the store's `.zattrs` when set). With `--ground`, each voxel is assigned to a layer by the height of its centre above the ground mesh; don't flatten the cloud with `raytranslate subtract` instead. `scripts/raydensity_tiles.sh cloud.ply store.zarr x0,y0 tile_width nx,ny zmin,zmax [jobs] [-- raydensity options]` runs both steps over all tiles in parallel and chooses the split halo, e.g. `raydensity_tiles.sh forest.ply forest.zarr 400000,6100000 25 12,12 1,4.3 32 -- --ground forest_mesh.ply --heights 0,0.6 --stem_diameter 0.01 --footprint 0.01,0.003,0.05`. See [`docs/large_scale_density.md`](docs/large_scale_density.md).

`raycreate pneumatophores 1` generates a synthetic hand-held scan of a pneumatophore field, plus the true profile (`pneumatophores_truth.csv`) and stem positions (`pneumatophores_stems.csv`), for testing these settings. Stems don't overlap and their number is exact for the density (`--overlapping` gives Poisson positions instead; `--min_gap 0.5` keeps stems at least half a diameter apart). Options include `--stems_per_m2`, `--diameter` (or `--diameter_sd` for log-normal diameters, `--diameter_mixture d1,d2,fraction` for two), `--clustered`, `--cluster_spread`, `--patchy`, `--footprint`, `--return_range`, `--trunks`, `--zenith`, `--walk_spacing`, `--rays` and `--truth_cells` (true cell densities); stem heights `--height mean,sd` (default 0.25,0.08; `--height 0.6,0` gives one height) or `--uniform_height min,max`; the scan `--scanner_height` (1.2 m) and `--plot_width` (6 m); measurement errors `--range_noise sd` and `--pose_noise sd,interval` (a smooth trajectory error, from a separate random sequence, so the stems and ideal rays are unchanged); and `--ground_returns` to keep the ground returns. Scenes are the same for a seed on any platform. `scripts/pneumatophore_seed_study.py`, `scripts/pneumatophore_cell_study.py`, `scripts/pneumatophore_trunk_study.py` and the report's study scripts (`scripts/pneumatophore_report_study.py`, `scripts/pneumatophore_self_shadow_study.py` and others, listed in its Section 12) evaluate estimates against the truth.

## Unit Tests

Unit tests must be enabled at build time before running. To build with unit tests, the CMake variable `RAYCLOUD_BUILD_TESTS` must be `ON`. This can be done in the initial project configuration by running the following command from the `build` directory: `cmake -DRAYCLOUD_BUILD_TESTS=ON ..`

Unit tests may then be run directly or using `CTest`.

### Running using CTest

To run using CTest:

* Change into the `build` directory
* Run `ctest .`

On some platforms it may be necessary to specify the build configuration to test. For example, the `Release` build may be tested using the modified command `ctest . -C Release`.

### Directly invoking the tests

When directly invoking the unit tests, is important that the tests are run from the directory to which the raycloud tools executables are built. To invoke the tests directly:

* Change into the `build` directory
* Change into the `bin/` directory
* Run `./raytest`

## Development Container Setup (.devcontainer)

This project provides a `.devcontainer` directory for consistent development environments. Using the devcontainer is optional, but recommended for a streamlined setup. Here's how to get started:

1. **Install Docker:** You'll need Docker Desktop (or a similar Docker engine) installed on your machine.

2. **Open in VS Code:**
    * Open the project in VS Code.
    * VS Code should automatically detect the `.devcontainer` folder and prompt you to "Reopen in Container". Click it.
    * If you're not prompted, open the command palette (Ctrl+Shift+P or Cmd+Shift+P) and type "Remote-Containers: Reopen in Container".

That's it! VS Code will handle building and running the development container for you. If you choose not to use the devcontainer, you will need to ensure your local environment matches the project's dependencies and requirements.

The scripts in [`.devcontainer/commands`](.devcontainer/commands) are available on PATH in the devcontainer and can be used to build, test and run raycloudtools and treetools. See [`.devcontainer/commands/setup.bash`](.devcontainer/commands/setup.bash) to configure CMake options and such.
