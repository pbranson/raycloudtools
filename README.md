## Ray Cloud Tools
A set of command line tools for processing ray clouds, together with an associated C++ library.


Ray clouds are point clouds with the sensor origin stored per point (currently encoded in the 'normal' field of .ply files).
Ray clouds represent free space as well as surfaces. This allows processing that cannot be done on point cloud data alone.

This is an open-source research library, a place to release new techniques in ray cloud analysis and manipulation. So if you would like to contribute with a new or improved method, do suggest it in our discussions page: https://github.com/csiro-robotics/raycloudtools/discussions.

## Install using a Pre-built Container

### Docker (Linux, MacOS, Windows)
#### Pull the Latest Image
To download the latest image from GitHub Packages, use the following command:
```bash
docker pull ghcr.io/csiro-robotics/raycloudtools:latest
```

#### Run an Interactive Container
To run the container interactively and bind your home directory to a directory inside the container for accessing host files:

#### On Linux/MacOS
```bash
docker run -it --name raycloudtools -v /home/yourusername:/workspace ghcr.io/csiro-robotics/raycloudtools:latest /bin/bash
```

#### On Windows
```bash
docker run -it --name raycloudtools -v C:/Users/YourUsername:/workspace ghcr.io/csiro-robotics/raycloudtools:latest /bin/bash
```
Replace `/home/yourusername` or `C:/Users/YourUsername` with the path to your home directory.

#### Reusing Container
To restart and attach to the container in the future:
```bash
docker start -ai raycloudtools
```

### Apptainer (Linux/HPC)
```console
# Login to GitHub Container Registry (required once)
export CR_PAT=YOUR_GITHUB_TOKEN
```

## Visualising Ray Clouds:
free software such as Meshlab and CloudCompare can view ray clouds.

The build variables RAYLIB_VISTOOL and RAYLIB_IMAGETOOL allow the --view (-v) flag to view command-line results immediately.
They default to meshlab and kolourpaint respectively but can be changed with ccmake or with the -D cmake argument.
You will need to install these programs if you want the --view flag to work.

## File format:
Raycloud files are loaded and saved in binary .ply format, the header section is text and follows this format:
```console
ply
format binary_little_endian 1.0
comment generated by raycloudtools library
element vertex 0000000000<number of points>
property <float/double> x
property <float/double> y
property <float/double> z
property <float/double> time
property <float/double> nx
property <float/double> ny
property <float/double> nz
property uchar red
property uchar green
property uchar blue
property uchar alpha
end_header
```
followed by the binary data. By default it uses floats for x,y,z,nx,ny,nz and doubles for time. nx,ny,nz is the vector from the end point x,y,z to the sensor's location at the time that the point was observed. It is not a surface normal, but the ray representing free space from point to source.

Imported .ply point cloud files have a similar format, but without the nx,ny,nz fields, and optionally an intensity field instead of the red,green,blue,alpha:
```console
ply
format binary_little_endian 1.0
comment Any comment here
element vertex 0000000000<number of points>
property <float/double> x
property <float/double> y
property <float/double> z
property <float/double> time
property <float/double> intensity
end_header
```
The range of this intensity mapped onto the raycloud's 0-255 alpha value using rayimport's max_intensity optional parameter.

The imported .laz point cloud format is the 3D point, time and intensity fields. Plus the optional colour field.

By default density assumes a spherical (isotropic) distribution of leaf angles (G = 0.5), giving leaf area per volume. For vertical stem-like elements such as mangrove pneumatophores, use `--density_model vertical_cylinder`. This applies G = sin(zenith) to each ray, so density is the frontal area per volume N·d (stems per m² × diameter, in m⁻¹), and pixel values are the frontal area index N·d·h. `--profile profile.csv` writes the density per height layer. Ground returns should be removed first (e.g. `rayextract terrain`, then set ground rays to zero alpha), so that they are treated as unobstructed rays rather than hits. On sloping ground, use `raydensity --ground` (below) for heights above ground, rather than flattening the cloud.

For thin stems scanned by hand-held lidar, a typical command, giving densities for 1 x 1 x 0.1 m cells, is:

```console
rayrender cloud.ply top density --density_model vertical_cylinder --estimator pooled --no_flat_top --stem_diameter 0.01 --footprint 0.01,0.003,0.05 --pixel_width 0.05 --min_bound -3,-3,0 --max_bound 3,3,0.6 --cells cells.csv --cell_size 1,1,0.1 --profile profile.csv
```

* `--footprint exit_diameter,divergence,threshold` corrects for the beam footprint, which makes thin stems appear wider (by about 2.5x for 1 cm stems in simulation). It needs the true mean stem diameter. The exit diameter and divergence (both at the 1/e^2 intensity level) are the scanner's per-pulse laser beam specification. The threshold (the fraction of the beam's power a stem must intercept to give a return) is not a published specification, and the result is sensitive to it (0.02 or 0.15 instead of 0.05 gives -13% or +30%), so calibrate it on a plot of known density.
* `--estimator pooled` (recommended) uses the path up to each hit (Beer-Lambert), pooled over a horizontal neighbourhood of +-`--pool_radius` (default 0.05 m). It is insensitive to voxel size, and corrects for the stems occupying space (see below). In simulation (5 cm voxels, beam footprint corrected, 8 scenes each), plot totals in the lowest two 0.1 m layers were within +10% for random stems from 100 to 1000 stems/m^2 (1.07 and 1.10 at 100 stems/m^2, 1.04 and 1.09 at 300, 0.96 and 1.03 at 1000) and 0.3 m patches (1.01 and 1.06), varying by under 1% between scenes. A larger `--pool_radius 0.1` reduces the high bias at lower densities (1.03 and 1.06 at 100 stems/m^2, 1.01 and 1.06 at 300) but reads low in small patches (0.92 and 0.98), so suits fairly uniform stands. See `docs/pneumatophore_density_method.md`.
* Stem occlusion correction (with `--stem_diameter`, disable with `--no_overlap_correction`): the free path between hits excludes the stems' cross-sections, as widened by the footprint, so the hit rate per free path overestimates N d, by 1 / (1 - solid fraction) and more where widened stems overlap. The response for non-overlapping stems is computed by a deterministic 2D simulation, and inverted using the stem diameter. The solid fraction N pi d^2 / 4 is limited to 0.4 (below the random packing limit of 0.547 for non-overlapping discs), so N d is at most 1.6 / (pi d): 51 m^-1, or 5100 stems/m^2, for 1 cm stems. The corrected density gives the true gap fraction exp(-N d L) of a horizontal path of length L through randomly placed stems.
* `--estimator crossing` counts each hit ray's path to the voxel exit (and through the stem's interior), which suits voxels holding few stems, and resolves patchiness at the voxel scale. It has no occlusion correction, so is biased low at high densities (about -10% at 300 stems/m^2 and -20% at 600 stems/m^2 with a beam footprint). The default (`beer_lambert`, unpooled) is biased high (+20 to +60% at 5 cm voxels) for discrete stems.
* `--cells` aggregates the voxels into coarser cells (e.g. for hydrodynamic models), giving the mean of the voxel estimates (recommended) and the pooled estimate. The pooled estimate is the same as using a single voxel the size of the cell with the default estimator: accurate (within about 5%) for uniform random stems, but 10-40% low where stems are patchy within the cell. The ratio of the two is therefore an indicator of patchiness within each cell.
* `--no_flat_top` disables the flat canopy top model (designed for grass and crops), which biases stems of varying height.
* Ray angles: steep rays hit stem tops, which the model doesn't include, so they overestimate layers containing the tops (by about +10 to +15% with all ray angles). `--min_sin_zenith` and `--max_sin_zenith` select a band of angles.
* In the profile, use the mean of the voxel densities rather than the pooled column when stems may be clustered: pooling across a layer underestimates clustered stems by 15-30%.

* `--min_gap 0.5` tells the occlusion correction that stems are at least this many diameters apart (surface to surface). More regular spacing leaves less free space between the footprint-widened stems: in simulation, assuming no gap when stems are 1 diameter apart overestimates by about 23% at 1000 stems/m^2 (and up to 10% at 300 stems/m^2).

**Large areas, and heights above sloping ground.** `raydensity` estimates one tile of a domain and writes its chunk of a Zarr store (readable by xarray, zarr-python and GDAL) of 3D cells, and optionally voxels. Tiles are independent, so they run in parallel, and they match a single run over the whole domain (to float rounding), as each tile uses the rays crossing a small halo around it:

```console
raysplit forest.ply tiles 400000,6100000 25 0.15 -10,50 12,12
raydensity forest_3_7.ply forest.zarr --origin 400000,6100000 --tile_width 25 --tiles 12,12 --tile 3,7 --ground forest_mesh.ply --heights 0,0.6 --stem_diameter 0.01 --footprint 0.01,0.003,0.05
```

`scripts/raydensity_tiles.sh` runs both steps over all tiles in parallel. `raysplit ... tiles` keeps each ray's start point (unlike `raysplit ... grid`), as the footprint correction needs the range from the scanner. With `--ground`, each voxel is assigned to a layer by its height above the ground mesh beneath it. Don't flatten the cloud with `raytranslate subtract` instead: it shifts each whole ray by the ground height at its end, misplacing the rest of the ray by the slope times its horizontal length. In simulation on a 10% slope, flattening underestimated by 30-50%, while `--ground` matched flat ground to within 1%. See `docs/large_scale_density.md`.

`raycreate pneumatophores 1` generates a synthetic hand-held scan of a pneumatophore field, plus the true profile (`pneumatophores_truth.csv`), for testing these settings. Stems don't overlap, and their number is exact for the density (a solid fraction above 0.5 is refused); `--min_gap 0.5` keeps stems at least half a diameter apart, and `--overlapping` instead gives independent (Poisson) positions. Options include `--clustered`, `--cluster_spread`, `--patchy`, `--stems_per_m2`, `--diameter`, `--footprint`, `--zenith`, `--walk_spacing` and `--truth_cells` (true cell densities). `scripts/pneumatophore_cell_study.py` evaluates cell estimates against the truth over scenes, estimators, voxel sizes and ray angles.

## Unit Tests

Unit tests must be enabled at build time before running. To build with unit tests, the CMake variable `RAYCLOUD_BUILD_TESTS` must be `ON`. This can be done in the initial project configuration by running the following command from the `build` directory: `cmake -DRAYCLOUD_BUILD_TESTS=ON ..`

Unit tests may then be run directly or using `CTest`.

### Running using CTest

To run using CTest:

* Change into the `build` directory
* Run `ctest .`

On some platforms it may be necessary to specify the build configuration to test. For example, the `Release` build may be tested using the modified command `ctest . -C Release`.

### Directly invoking the tests

When directly invoking the unit tests, is important that the tests are run from the directory to which the raycloud tools executables are built. To invoke the tests directly:

* Change into the `build` directory
* Change into the `bin/` directory
* Run `./raytest`

## Development Container Setup (.devcontainer)

This project provides a `.devcontainer` directory for consistent development environments. Using the devcontainer is optional, but recommended for a streamlined setup. Here's how to get started:

1. **Install Docker:** You'll need Docker Desktop (or a similar Docker engine) installed on your machine.

2. **Open in VS Code:**
    * Open the project in VS Code.
    * VS Code should automatically detect the `.devcontainer` folder and prompt you to "Reopen in Container". Click it.
    * If you're not prompted, open the command palette (Ctrl+Shift+P or Cmd+Shift+P) and type "Remote-Containers: Reopen in Container".

That's it! VS Code will handle building and running the development container for you. If you choose not to use the devcontainer, you will need to ensure your local environment matches the project's dependencies and requirements.

The scripts in [`.devcontainer/commands`](.devcontainer/commands) are available on PATH in the devcontainer and can be used to build, test and run raycloudtools and treetools. See [`.devcontainer/commands/setup.bash`](.devcontainer/commands/setup.bash) to configure CMake options and such.
